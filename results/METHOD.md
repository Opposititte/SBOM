# 方法 — SBOM 精度の結果をどう作ったか

このドキュメントは `results/metrics.md` の数値を、最初から最後までどう作ったかを説明します。
各リポジトリは4つのステップを通り、最後の5ステップ目で全体を比較します。

---

## ステップ1 — リポジトリのクローン
```bash
git clone --depth=1 https://github.com/<owner>/<repo>.git
```
`--depth=1` は**浅いクローン**で、git の履歴ではなく最新スナップショット（現在のファイル）
のみを取得します。SBOM ツールが読む `go.mod`/`go.sum`/ソースはフルクローンと同一なので、
**クローンの深さは結果に影響しません**。

## ステップ2 — 正解データ(GT)の作成
```bash
go list -m all > gt_go_list.txt
```
`go list -m all` は Go ツールチェイン自身に**ビルドリストの全モジュール**を尋ねます。
これを「正解」とみなします。出力は1行1モジュール（`<パス> <バージョン>`）です。先頭行は
プロジェクト自身なので、後で除外します。

## ステップ3 — 3つのSBOMツールで走査
```bash
syft   <folder> -o cyclonedx-json=syft_output.json
trivy  fs <folder> --format cyclonedx --output trivy_output.json
cdxgen <folder> -o cdxgen_output.json
```
各ツールは CycloneDX 形式の JSON を出力します。Go の依存は
`pkg:golang/github.com/davecgh/go-spew@v1.1.1` のような purl を持つコンポーネントとして現れます。

## ステップ4 — クローンを削除
GT と走査結果を保存すればソースコードは不要なので、ディスクを空けるためクローンを削除します。
残すのは小さなテキスト/JSON の出力だけです。

## ステップ5 — 正解(GT)と走査結果の比較
これは保存済みの全結果に対して一度だけ実行します（`compute_metrics.js`）。
各（リポジトリ, ツール）の組について:

1. GT をモジュールパスの集合にする。
2. ツールの JSON から `pkg:golang/` のコンポーネントだけを取り出し、別の集合にする。
3. 重なりを数える:
   - **TP**（真陽性）  = 報告した、かつ正解にある
   - **FP**（偽陽性） = 報告したが正解に無い
   - **FN**（偽陰性） = 正解にあるが報告しなかった
4. 計算する:
   - **Precision** = TP / (TP + FP) — 報告したもののうち正しかった割合
   - **Recall**    = TP / (TP + FN) — 実際の依存のうち見つけた割合
   - **F1**        = 2·P·R / (P + R) — Precision と Recall のバランス

### 名前一致 と バージョン一致
- **名前一致 (name-level):** モジュールの*パス*だけ一致すればよい。
- **バージョン一致 (F1 ver):** パス**かつ**正確なバージョンの一致が必要。
- 両者はほぼ同じ ⇒ ツールはモジュールを見つけたとき、大抵バージョンも正しい。

---

## 範囲と公平性についての注意
両側とも Go モジュール（`pkg:golang/`）のみを比較します。Go 以外のコンポーネント（npm,
GitHub-Actions, generic）と `stdlib` は無視します。正解（`go list -m all`）が Go モジュールのみを
含むためです。マルチモジュール構成（例: gorm）ではルートの `go list` が兄弟モジュールを
取りこぼし、それが偽陽性として現れることがあります（`metrics.md` の注意点を参照）。

## なぜ True Negative (TN) を使わないか
混同行列には TP / FP / FN / **TN** の4つがありますが、本研究では TN を使いません。
- **TN**（真陰性）= 「依存ではなく、かつツールも報告しなかったもの」。
- その対象は「このリポジトリの依存ではない、世界中のすべての Go モジュール」になり、**事実上無限**で
  数えられず、意味もありません（「無関係な数百万パッケージを正しく挙げなかった」という情報に価値はない）。
- さらに Precision = TP/(TP+FP)、Recall = TP/(TP+FN)、F1 はいずれも **TN を使いません**。
  TN が必要なのは Accuracy や Specificity ですが、これらは有限の「陰性集合」を前提とするため、
  陰性集合が無限な依存検出タスクには不適切です。
- 結論: 依存検出は情報検索（information retrieval）型の評価であり、**Precision / Recall / F1**
  が標準的で適切な指標です。

## なぜ name（名前）と version（バージョン）を分けるか
purl（例: `pkg:golang/github.com/davecgh/go-spew@v1.1.1`）は「パス（識別子）」と「バージョン」の
2つの情報を持ちます。これを分けることで、2つの異なる問いを別々に測れます。
- **名前一致:** ツールはその依存を**そもそも見つけられたか**。
- **バージョン一致:** ツールは**バージョンまで正しく**特定できたか。

**なぜ version が重要か:** 脆弱性（CVE）は**特定のバージョン**に紐づきます（例: log4j 2.14 は脆弱、
2.17 は修正済み）。バージョンが分からないと、ツールは「自分が脆弱かどうか」を**自動で判定できず**、
人手で go.sum 等を確認する必要が生じ、誤検知も増えます。依存が数百件・CVE が日々増える環境では
自動化が必須であり、そのためにバージョン精度が重要です。本研究の結果では、ツールは依存を見つけた
場合ほぼ正しいバージョンを報告しており、両者の F1 はほぼ同じになります。

## go.mod / go.sum / `go list -m all` の違い（なぜ正解に go list を選んだか）
- **go.mod** = 人が編集する宣言ファイル。主に**直接依存**（と最小バージョン）を記載。
- **go.sum** = 依存グラフ上の**全モジュール（推移的依存も含む）**のチェックサム。直接依存より多くを含むが、
  かつて検討された版なども残るため、実際のビルドより**過剰**になりうる。
- **`go list -m all`** = Go ツールチェインが計算した**実際のビルドリスト**（推移的依存込み・過不足なし）。
  もっとも正確なので、本研究の**正解 (GT)** に採用しました。
