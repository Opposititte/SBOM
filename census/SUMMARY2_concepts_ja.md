# census 補遺：用語・依存グラフ・go.sum の考え方（混乱しやすい所メモ）

`SUMMARY_census.md` の数字を理解するための背景。**後で混乱したらここを見る用**。

---

## 0. 用語（まずこれ）

- **ルート ＝ 自分のプロジェクト**：解析対象のリポジトリ（blocky 等、または実験で作った `example.com/myapp`）。あなたが書いたコード。
- **依存（dependency）**：ルートが引き込む他人のライブラリ（testify, objx …）。
- **グラフ（dependency graph）**：**「どのモジュールがどのモジュールを require するか」の矢印ネットワーク**。家系図・組織図のようなもの。
  **二次関数の x-y グラフとは無関係。** 「グラフに居る/外れる」＝「依存ネットワークに矢印で繋がっているか/いないか」。

```
myapp（ルート＝自分）
  └─import→ testify ──require→ objx ──require→ …
               └ testify自身が使う go-spew / go-difflib / yaml
```

## 1. 「testify はテスト依存では？なぜ GT-imported に入る？」← 一番混乱する所

**GT-imported に入るかは「testify がテスト用ライブラリか」ではなく「どこで import したか」で決まる。**

| どこで import したか | GT-imported（非test） | GT-impT（+test） |
|---|---|---|
| **ケース1: `app.go`（通常コード）で import** | testify **入る** | 入る |
| **ケース2: `app_test.go`（テストファイル）だけで import** | testify **入らない（空）** | testify **入る** |

（`/tmp` で実験して確認済み。）

- testify を「本来の使い方（`_test.go` でだけ使う）」にすると **GT-imported には入らず、GT-impT にだけ入る**。
- 私の最初の説明は testify を `app.go`（通常コード）で import していたので紛らわしかった。**testify そのものがテスト依存なのではなく、「テストファイルでしか使わなければテスト依存」**。
- これが GT-imported と GT-impT を分ける意味そのもの：**impT − imported ＝ テストでしか使わない依存**。

## 2. 質問A：GT-all の「未使用依存」の正体は？

**Q（A）**: GT-all（build list）には、実際に使う分（imported）よりずっと多くのモジュールが入る。その「未使用」の正体は？なぜそんなに多い？

**A（回答）**: 未使用の大半は **「あなたのコードが import しない、依存の依存（深い推移的依存）」**。5リポジトリ集計：

| 未使用の分類 | 割合 | 意味 |
|---|---:|---|
| 深い間接（go.mod にも無い） | **70%** | 依存の依存。あなたのgo.modにすら載らない |
| go.mod の `// indirect` | 26% | tidy が記録した間接依存 |
| 他OS（win/darwin用） | 3% | GOOS=linux計測なので他OS専用は未使用扱い |
| 直接依存だが未使用 | **1%** | ほぼ無い（＝直接requireはちゃんと使われている） |

→ **「使わない直接依存を書きすぎ」ではない。** 主因は「1つ使うために芋づる式に付いてくる依存の依存」。
規模感：blocky で imported 128 → all 334（約2.6倍）。corpus全体で all は impT の中央値2.2倍。

## 3. 質問B：未使用モジュール B の依存木も build list に入るのか？

**Q（B）**: ルートが依存Aをimportし、Aが未使用モジュールBを require するとき、GT-all には **B が require する依存木も** 入るのか？

**A（回答）**: **入る（カスケードする）。** 実験（testify/assert だけ import）：
- ルート `myapp` は testify を import
- testify は `objx` を require（testify/mock が使う）。assert は objx を使わない
- **それでも objx は GT-all に入る**（グラフ上に居るから）。しかも myapp の go.mod には載らない
- 同様に yaml が require する `check.v1` も GT-all に入る

→ **「1つ import すると、その依存が require するモジュール群がグラフ経由で GT-all にごっそり入る」**。ただし無限ではなく、次項の刈り込みで止まる。

**imported と all の違いを一言で**：
- **GT-imported** ＝ 矢印を「実際に import する所」だけ辿った集合（objx には辿り着かない）
- **GT-all** ＝ グラフ上の（刈り込み範囲内の）全モジュール（objx も含む）

## 4. 「刈り込み（pruning）の範囲」はどう決まるか

`go list -m all`（GT-all）は無限に広がらない。Go 1.17 で入った**モジュールグラフの刈り込み**で範囲が決まる。ルール：

1. **ルートの `go` ディレクティブが 1.17 以上** → 刈り込み有効（グラフを絞る）。1.17未満 → 刈り込み無し（全推移的閉包が入り、もっと広がる）。
2. **各依存モジュールごとに**：
   - その依存が **go 1.17+** を宣言 → その依存の **直接 require まで**をグラフに入れる（さらにその先の推移的requireは切る）。
   - その依存が **go 1.17未満** → その依存の **全推移的依存**をグラフに入れる（旧仕様のため丸ごと）。
3. さらに、あるモジュールの**パッケージを実際に import している**場合は、その require が読み込まれる。import しないモジュールは「一段先まで」で止まりやすい。

つまり範囲は **「ルートと各依存の go バージョン」＋「どのモジュールのパッケージを実際に import するか」** で決まる。
実務上は、依存同士が同じモジュールを共有するため、切られたつもりの依存が別経路でグラフに現れることも多い（だから実測では「綺麗に切られた」例が見えにくい）。

**要点**：GT-all は「imported の約2〜3倍」に膨らむが、go 1.17+ の刈り込みのおかげで**有限で止まる**（1.16以前なら全閉包でもっと膨らむ）。

## 5. go.sum と `go mod tidy`（Cの確認）

| 状態 | go.sum での扱い |
|---|---|
| **グラフから外れた依存**（もう誰も require しない） | `go mod tidy` で **全バージョン完全に消える**（logrus実験：13行→2行） |
| **まだグラフ内の依存** | 残る。さらに **MVS（最小バージョン選択）用に複数バージョンの go.mod ハッシュ**も残る（go-spew：v1.1.0/1.1.1/1.1.2 の3版の go.mod ハッシュ＋選ばれた1版の zip ハッシュ） |

- **go.sum は go.mod より広い**：blocky で go.mod requires **194** vs go.sum **334モジュール**。go.mod は刈り込み済みの記録、go.sum はグラフ全体をカバー。
- 「複数バージョンが残る」のは **まだ使われている依存**の話。**消された依存が残るのではない**（そこは完全削除）。

**go.sum の役割**：依存の中身が改ざんされていないか検証するハッシュ台帳（go.mod が「何を使うか」の宣言、go.sum が「その中身の指紋」）。
