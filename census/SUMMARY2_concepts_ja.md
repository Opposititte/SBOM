# census 補遺：用語・依存グラフ・go.sum の考え方（混乱しやすい所メモ）

`SUMMARY_census.md` の数字を理解するための背景。**後で混乱したらここを見る用**。

---

## 0. 用語（まずこれ）

- **ルート ＝ 自分のプロジェクト**：解析対象のリポジトリ（blocky 等、または実験で作った `example.com/myapp`）。あなたが書いたコード。
- **依存（dependency）**：ルートが引き込む他人のライブラリ（testify, objx …）。
- **グラフ（dependency graph）**：**「どのモジュールがどのモジュールを require するか」の矢印ネットワーク**。家系図・組織図のようなもの。
  **二次関数の x-y グラフとは無関係。** 「グラフに居る/外れる」＝「依存ネットワークに矢印で繋がっているか/いないか」。

```
myapp（ルート＝自分）
  └─import→ testify ──require→ objx ──require→ …
               └ testify自身が使う go-spew / go-difflib / yaml
```

---

## 1. 「testify はテスト依存では？なぜ GT-imported に入る？」← 一番混乱する所

**GT-imported に入るかは「testify がテスト用ライブラリか」ではなく「どこで import したか」で決まる。**

| どこで import したか | GT-imported（非test） | GT-impT（+test） |
|---|---|---|
| **ケース1: `app.go`（通常コード）で import** | testify **入る** | 入る |
| **ケース2: `app_test.go`（テストファイル）だけで import** | testify **入らない（空）** | testify **入る** |

（`/tmp` で実験して確認済み。）

- testify を「本来の使い方（`_test.go` でだけ使う）」にすると **GT-imported には入らず、GT-impT にだけ入る**。
- 私の最初の説明は testify を `app.go`（通常コード）で import していたので紛らわしかった。**testify そのものがテスト依存なのではなく、「テストファイルでしか使わなければテスト依存」**。
- これが GT-imported と GT-impT を分ける意味そのもの：**impT − imported ＝ テストでしか使わない依存**。

## 2. 質問A：go.mod にある「実際に使わない依存」とは何で、なぜ tidy しても残るのか

**Q（A）**: go.mod は `go mod tidy` すれば未使用依存が消えるはず。なのに「実際には使わない依存が含まれる」とはどういうこと？その正体と原因は？

**A（回答・実測 by blocky）**: blocky の go.mod 194件のうち、linux非testで実importされないのは66件。その内訳：
- test で使う（自分のテスト）: 4
- 他OS（win/darwin）で使う: 6
- **どのビルドでも使わない「真の未使用」: 56** ← これが問題の本体（全て `// indirect`、tidyしても194→194で消えない）

**その56件の正体は、`go mod why` で追うと主に2種類：**

| 原因 | 例 | 仕組み |
|---|---|---|
| **① コード生成ツールの依存**（最大） | go-enum, mockery, oapi-codegen とその依存(sprig, go-md2man, kin-openapi…) | go.mod の **`tool` ディレクティブ**で宣言し `//go:generate go tool ...` で呼ぶ。ツールを動かすのに必要なので tidy は消さない。**でもツールはアプリのバイナリにコンパイルされない**ので `go list -deps`(=GT-imported) には出ない＝「使わないのにある」 |
| **② 依存の"テスト"が要求する依存** | fsnotify（`go-redis/redis/v8.test` が使う） | あなたが使う go-redis の**テストコード**が import。あなたはそのテストを実行しないが、go-redis の go.mod が要求するのでグラフに記録される |

→ **結論：「使わない直接依存を書きすぎ」ではない。** go.mod の未使用は、ほぼ **「開発ツールの依存」＋「依存のテストが使う依存」**。どちらもアプリ本体には不要だが、`tool`宣言や依存のgo.modが要求するので `go mod tidy` は消さない（消すと開発・再現ビルドが壊れる）。

## 3. 質問B：GT-all はどこまで深く依存を辿るのか（深さを決めるアルゴリズム）

**Q（B）**: `go list -m all`（GT-all）は、依存の依存の依存…をどこまで深く出すのか？「第N層まで」なのか？その深さを決めるロジックは？

**A（回答）**: **「第N層」ではない。** モジュールを1個ずつ「展開するか否か」判定していく**グラフ探索**で決まる。`go mod graph` で実証：
- **testify（import する＝使う）** → 展開される：`testify→go-spew`, `testify→objx`, `testify→yaml` と**出る辺がある**（go.modを読んで要求を足す）
- **objx（import しない＝使わない）** → **展開されない**：`objx→…` の辺は**ゼロ**。objxは GT-all に**名前は載る**が、**その先の依存は辿られない（打ち切り）**

### アルゴリズム（Go 1.17+ モジュールグラフ刈り込み）
ルートから辿り、各モジュール M を「**展開するか（Mのgo.modを読み、その要求を新ノードとして足すか）**」判定：

**Mを展開する条件:**
1. **Mのパッケージが、ビルド/テストで実際に import されている**（M is used） … ✅本調査で実証
2. **M が `tool` ディレクティブのツール**（go-enum 等）＝ import扱いになるので①同様に展開 … ✅実証（mockery: 自コードのimport 0 でも GT-all 61個）

**どちらも満たさない M** → 展開しない。**名前だけ GT-all に1回載せて、その先は切る**（objx がこれ） … ✅実証（`go mod graph` で objx は出る辺ゼロ）

⚠️ **未実証の但し書き**：Go公式ドキュメントは「**go 1.17 未満のモジュールは刈り込み対象外（全展開）**」とするが、**本調査ではローカルの制御実験で再現できていない**（replaceがグラフを短絡させた可能性）。実証済みは上記①②と打ち切りのみ。

`go list -m all`（GT-all）＝ この刈り込みグラフの**全ノード**（MVSでバージョン確定後）。

### だから深さは
- **使うモジュールの連鎖**：どこまでも深く辿る（使う限り止まらない）… ✅実証
- **使わないモジュール**：到達した所で**名前だけ載せてその先を切る**（objx）… ✅実証
- **ツール**：`tool`宣言のツールは import扱いなので依存木を全部引き込む（mockeryで61個）… ✅実証。ただしツール自身の未使用siblingは打ち切り（example-go-repo）… ✅実証
- （go<1.17 の全展開はGo仕様上あり得るが**本調査では未確認**）

**一言で**：「使うもの（ツール含む）は奥まで辿る／使わないものは名前だけ載せて打ち切る」。層数ではなく、この**展開判定の連鎖**が深さを決める。

**GT-all の正体**：だから GT-all は「アプリの依存」ではなく、**アプリの依存 ＋ 開発ツールの依存木 ＋ 依存のテスト依存 ＋ それらの直接require**まで含んだ「モジュールグラフ全体」。blocky で imported 128 → all 334（約2.6倍）に膨らむ主因はこれ。**GT-all と GT-imported+test の大差の本質＝この"ツール・テスト・未使用sibling"の混入**。

## 5. go.sum と `go mod tidy`（Cの確認）

| 状態 | go.sum での扱い |
|---|---|
| **グラフから外れた依存**（もう誰も require しない） | `go mod tidy` で **全バージョン完全に消える**（logrus実験：13行→2行） |
| **まだグラフ内の依存** | 残る。さらに **MVS（最小バージョン選択）用に複数バージョンの go.mod ハッシュ**も残る（go-spew：v1.1.0/1.1.1/1.1.2 の3版の go.mod ハッシュ＋選ばれた1版の zip ハッシュ） |

- **go.sum は go.mod より広い**：blocky で go.mod requires **194** vs go.sum **334モジュール**。go.mod は刈り込み済みの記録、go.sum はグラフ全体をカバー。
- 「複数バージョンが残る」のは **まだ使われている依存**の話。**消された依存が残るのではない**（そこは完全削除）。

**go.sum の役割**：依存の中身が改ざんされていないか検証するハッシュ台帳（go.mod が「何を使うか」の宣言、go.sum が「その中身の指紋」）。
