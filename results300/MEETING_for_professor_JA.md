# 卒論 中間相談 資料（Go言語の SBOM 精度評価）

> **一言サマリ（TL;DR）**
> SBOM ツールの「正確さ」は **正解(GT)の定義に依存する**。`go list -m all`（全グラフ）を正解にすると
> **syft が最良**だが、`go list -deps`（実際に使う依存＝imported）を正解にすると **cyclonedx-gomod / cdxgen が最良**に逆転する。
> 各ツールの「取りこぼし」は **ほぼ全てが“実際には使われない依存”**（テスト専用・未使用）で、真の見逃しは **1%未満**。
> → 「ツールはどの依存定義を出力するか明示すべき」「用途で選ぶべき」が本研究の主張。

---

## 1. 研究の位置づけ（先行研究との差分）

| | 先行研究 Yu et al. (DSN 2024) | 本研究 |
|---|---|---|
| 対象言語 | Python 中心（9言語横断） | **Go 専用に深掘り** |
| 主手法 | 差分分析（ツール同士の比較）。正解が無いため | **正解(GT)を作って精度を直接測定** |
| 正解(GT) | `pip install` ドライラン＝**all 相当のみ** | **all / imported / direct の3定義で比較** |
| def-use | 「実装すべき」と**提案のみ（未実装）** | `go list -deps` で **imported を実装** |
| 同僚 Pei との差 | （Python/uv） | **Go エコシステム** |

**主張できる貢献:** Yu らが「やるべき」と言った *def-use 的な正解(imported)* を Go で実現し、
**「最良ツールは正解定義で入れ替わる」**ことを 216/190 リポジトリ規模で定量化した。

---

## 2. 正解(GT)の3定義 — ここが相談の核心

| 正解 | 意味 | 作成コマンド | 含むもの |
|------|------|-------------|---------|
| **all** | モジュールグラフ**全体** | `go list -m all` | 直接＋間接＋**テスト専用＋未使用**の推移依存も全部 |
| **imported** | 実際に**コンパイルされる**＝使う依存 | `go list -deps -f '{{with .Module}}{{.Path}} {{.Version}}{{end}}' ./... \| sort -u` | 直接＋実際に使う間接（テスト専用・未使用は除外） |
| **direct** | go.mod の**直接宣言**のみ | `go mod edit -json`（`Indirect` でない `Require`） | 自分で書いた直接依存だけ |

関係: **direct ⊆ imported ⊆ all**
先行研究は **all 相当のみ**を正解にした（＝「使われない依存」も正解に含めてしまう）。

---

## 3. 結果① ツール × 正解定義 の F1（％, 300件平均）★メイン結果

| ツール | vs **all** | vs **imported** | vs **direct** |
|--------|------:|------:|------:|
| **syft** | **71.4** ◀ | 63.9 | 43.6 |
| **trivy** | 70.7 | 65.4 | 44.2 |
| **cdxgen** | 55.5 | 90.7 ◀ | 57.2 |
| **cyclonedx-gomod** | 53.1 | **94.0** ◀ | 54.6 |

- 正解=**all** → **syft / trivy が勝つ**（推移依存まで読むから）。
- 正解=**imported** → **cyclonedx-gomod / cdxgen が勝つ**（実際に使う依存を正確に出すから）。
- **同じツール・同じデータでも、正解を変えると勝者が逆転する。** ← 図 `charts/f1_heatmap.png`

**実例（piper, all=160 / imported=15）:** trivy は 161 個報告 → **vs all=100%** だが **vs imported=17%**。
cdxgen / cyclonedx-gomod は 15 個 → **vs imported=100%**。

---

## 4. 結果② なぜ取りこぼすのか（原因分解）★考察の核心

`all` に対して各ツールが取りこぼした依存を「**実際には使われない（テスト/未使用）**」か「**本当に使うのに見逃し**」かで分解（189件合算）:

| ツール | 取りこぼし計 | 使われない依存(=報告しなくて正常) | **本当の見逃し** | 過剰報告(FP) |
|--------|----:|----:|----:|----:|
| syft | 10,189 | 99.9% | **0.1%** (10) | 1,787 |
| trivy | 11,041 | 99.9% | **0.1%** (10) | 1,724 |
| cdxgen | 15,241 | 91.8% | **8.2%** (1,249) | 378 |
| cyclonedx-gomod | 13,558 | 99.0% | **1.0%** (138) | **14** |

- **「all に対する Recall の低さ」はツールの欠陥ではなく、正解 all が“使われない依存”まで含むため。**
  実際に使う依存はほぼ取りこぼさない（真の見逃し <1%、cdxgen のみ 8.2%）。
- **過剰報告(FP):** syft/trivy が多い（マルチモジュールの兄弟依存を拾う＝gorm型）。
  cyclonedx-gomod は FP=14 と極めてクリーン。 ← 図 `charts/rootcause_stacked.png`

---

## 5. 結果③ 規模とバージョン（補足）

- **規模依存:** リポジトリが大きいほど `all` に対する Recall が下がる（テスト/推移依存が増えるため）。 ← 図 `charts/recall_vs_size.png`
- **バージョン精度:** 「purl＋バージョン一致」でも F1 は name 一致とほぼ同じ（差 〜0.7pt）。
  **ツールは依存を検出できればバージョンも正しく出す**（CVE 照合に重要）。

---

## 6. 改善提案（たたき台）

1. **ツールは「どの依存定義(all/imported/direct)を出力するか」を明示すべき**（評価もその定義で行う）。
2. **用途でツールを選ぶ:**
   - 脆弱性を漏れなく洗う（テスト依存も含む）→ **syft / trivy（all）**
   - 配布物に実際に含まれる依存を正確に → **cyclonedx-gomod / cdxgen（imported）**
3. **ハイブリッド案（Yu らの def-use 提案の具体実装）:** syft 等の all 出力に `go list -deps` を後処理で重ね、
   各依存に「実際に使う/使わない」フラグを付与 → **脆弱性の誤検知を削減**。
4. **マルチモジュール対応:** ルートだけでなくネスト各モジュールで GT を取り、gorm 型の過剰報告(FP)を解消。
