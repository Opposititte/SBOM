# 実験設計（Go言語の SBOM 精度評価）

迷ったらここに戻る「地図」。

## 目的（リサーチクエスチョン）
1. SBOM生成ツールは、Goプロジェクトの依存関係を **どれだけ正確に** 出力できるか？
2. その「正確さ」は **正解(GT)の定義に依存する** のではないか？
3. ツールが **間違える原因は何か**（なぜ取りこぼし・余計な報告が起きるか）。
4. それを踏まえて **どう改善できるか**（手法の提案）。

→ 本研究の柱は **「精度の測定」＋「原因分析」＋「改善手法」**。

## 正解(GT)の3定義 と 作成コマンド
| 正解 | 意味 | コマンド |
|---|---|---|
| **all** | モジュールグラフ全体（テスト用・未使用の依存も含む） | `go list -m all` |
| **imported** | 実際にコードで使う（コンパイルに取り込まれる）モジュール | `go list -deps -f '{{with .Module}}{{.Path}} {{.Version}}{{end}}' ./... \| sort -u` |
| **direct** | go.mod に直接宣言した依存だけ | `go mod edit -json`（`Require` の非 `Indirect`） |

関係：**direct ⊆ imported ⊆ all**

## 評価指標
- **Precision（適合率）/ Recall（再現率）/ F1**
- name 一致（モジュール名）と version 一致（名前＋バージョン）の両方。

## 対象・ツール
- **対象：awesome-go に掲載された全 Goリポジトリ（約2,723件）**。
  （現状は 6件で詳細分析＋約300件で予備実験。最終的に全件へ拡大する。）
- **ツール4種：syft / trivy / cdxgen / cyclonedx-gomod**。

## 手順
1. リポジトリをクローン
2. 3つの正解(all / imported / direct)を作成
3. 4ツールで SBOM を生成
4. 各ツールの出力を各正解と照合し、Precision / Recall / F1 を算出
5. 取りこぼし・余計な報告の原因を分解して分析
6. 改善手法を提案

## これまでの主な結果（予備実験）
- **「最も正確なツール」は正解の定義で入れ替わる**：
  - 正解=all → **syft / trivy** が最良。
  - 正解=imported → **cdxgen / cyclonedx-gomod** が最良。
- ツールの「取りこぼし」の**ほぼ全ては“実際には使われない依存（テスト用・未使用）”**で、本当に使う依存の見逃しは1%未満。
- バージョンまで一致を求めても結論は変わらない（ツールはバージョンも概ね正しく出す）。

## 先行研究との差分（簡単に）
- 先行研究 Yu et al.(2024) は **Python 中心**で、正解は **「全グラフ(all 相当)」のみ**を使った。
  そして「**宣言された依存が、実際にコードで使われているかまで見るべき**」と**提案だけ**して、実装はしていない。
- 本研究は **Go** で、それを**実装**した（＝**imported**：実際に使う依存を正解にする）。さらに **3つの正解で比較**し、
  「最良ツールは正解の定義で変わる」ことを定量的に示す。

## 妥当性についての注意（サンプリング）
- **対象を awesome-go の全リポジトリにするので、ランダム抽出による「サンプリングの偏り」は生じない**（母集団そのものを使うため）。
- ただし、妥当性の注意として次は明記する：
  1. **awesome-go は人手で選ばれたリスト**なので、「Go言語の全プロジェクト」を代表するわけではない（母集団の選択という限界）。
  2. **非Go・ビルド不能・アーカイブ済み**のリポジトリは評価対象から外れる。
  3. 結果は **ツールのバージョン・Goのバージョン** に依存する。
  4. マルチモジュール構成のリポジトリでは、正解をルートだけにするか各モジュール和集合にするかで結果が変わる。

## 残りの検討事項（教授と相談）
- 主正解を all＋imported とする方針でよいか（direct は補助）。
- 全2,723件へ拡大する時期。
- 改善手法を「提案」までか「実装・評価」まで踏み込むか。
- ツールを4種で十分か（SPDX系を追加するか）。
