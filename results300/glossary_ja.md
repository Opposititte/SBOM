# 用語集・仕組みメモ（初心者向け / cobra 実例つき）

卒論の背景・口頭発表の準備用。すべて spf13/cobra の実例で確認済み。

## 0. いちばん大事な階層（Go）
```
ソースファイル(.go)  <  パッケージ(フォルダ)  <  モジュール(プロジェクト全体・go.mod が1個)
```
- **パッケージ = フォルダ1つ**。その中の全 `.go` ファイルで1パッケージ。
- **モジュール = フォルダ(パッケージ)を集めたプロジェクト全体**。`go.mod` が目印。1リポジトリ＝1モジュールが普通。
- cobra の実例: ルートフォルダ(.go 25個)=パッケージ`cobra`、docフォルダ(.go 11個)=パッケージ`cobra/doc`。
  この2パッケージをまとめた全体がモジュール`github.com/spf13/cobra`。

## 1. パッケージが「使われる」とは
別のコードが `import "そのパッケージ"` と書き、その中の**公開（大文字始まり）の関数・変数を実際に呼ぶ**こと。
import して実際に呼ばれている＝「使われている(imported)」。

## 2. go list のコマンドの違い
| コマンド | 何を並べる | cobra の結果 |
|---|---|---|
| `go list ./...` | **パッケージ**（自分のフォルダ） | 2個（cobra, cobra/doc） |
| `go list -m` | **モジュール**（自分のプロジェクト） | 1個（cobra） |
| `go list -m all` | 自分＋**依存している他人のモジュール全部** | 7個 |
| `go list -deps ./...` | 実際に import で**たどり着くパッケージ全部** | （多数→モジュールに直すと重複） |

- `./...` … 「今のフォルダ以下を全部（再帰）」を表す記号。`.`=今のフォルダ、`...`=その下も全部。
- `-m` … module（モジュール単位で見る）。`-m all` の `all` … 依存も含めた全モジュール。
- 依存先（go-md2man 等）も**他人が作った1モジュール**。だから `-m all` は複数並ぶ。

## 3. 3つの正解(GT)と作り方
```
direct（go.mod に直接宣言）⊆ imported（実際にコンパイルされる）⊆ all（グラフ全体）
```
```bash
go list -m all                                                  # all
go list -deps -f '{{with .Module}}{{.Path}} {{.Version}}{{end}}' ./... | sort -u   # imported
go mod edit -json    # .Require のうち Indirect でないもの         # direct
```
- `sort -u` … 並べ替え＋重複削除。`go list -deps` は「1パッケージ=1行」で出すため、同じモジュールが
  何度も出る（cobra は2パッケージあるので2回）。それを「1モジュール=1行」にまとめる**表示の整形**。
  （実体は何も消さない。）
- `go list -m all` は最初から「1モジュール=1行」なので sort -u 不要。

## 4. all と imported の「動き方」の違い（重要）
- **all = go.mod だけを読む**。自分の go.mod → 依存の go.mod → … と**宣言書を再帰的にたどる**。
  ソースコードは見ない。だからテスト用・未使用の依存も全部入る。
- **imported = 実際のソースの `import` をたどる**。自分の `.go` の import → その先の import → … と
  **本当に使う経路だけ**たどる。だから速度は遅め・依存先のソース取得も要る（all より重い）。

## 5. テスト専用ファイルの除外ルール
- Go の公式ルール: **ファイル名が `_test.go` で終わる = テスト専用** → 通常ビルドから除外。
- 文字列ヒューリスティックではなく言語仕様。`args.go`(本番) と `args_test.go`(テスト) は同じフォルダに同居。
- 意図に関係なく**語尾が `_test.go` なら無視**される（例: `foo_test.go`）。本番で使うなら語尾を変える。
- 同様に `xxx_windows.go` 等は OS 別ファイルで、対象 OS のときだけビルドされる
  （cobra の mousetrap が Windows だけ imported に出るのはこのため）。

## 6. テストとは / なぜ test 依存が本番に入らないか
- テスト = 「製品がちゃんと動くか確かめる」作業。`check.v1`/`testify` 等は**確かめるための道具**。
- 道具は製品に積まれない（車の検査機械を車に積まないのと同じ）→ 本番ビルドに入らない。

## 7. git / コミット / --depth=1
- **コミット** = 変更を保存した1つのセーブポイント（スナップショット）。
- **コミット履歴** = 最初から今までのセーブの積み重ね。
- `git clone` = 履歴を全部取得。`--depth=1` = **最新の1コミットだけ**取得（履歴は取らない）。
  - depth はバージョンではなく**git履歴の深さ**。`--depth=2`=最新2コミット（=直近2回の編集、バージョンではない）。
- なぜ default が履歴全部か: git は開発者が過去を見る/戻すツールだから。解析・利用は最新だけでよく、
  `--depth=1` が高速・軽量で正解。

## 8. go.mod はいつ作られ/更新されるか
- 作成: プロジェクト開始時 `go mod init`。
- 更新: 依存を変えるコマンドを打ったとき → `go get`（追加/更新）, `go mod tidy`（整理）, `go build/test`（補完）。
- 常時自動ではない。

## 9. def-use 解析とは / 本研究の位置づけ
- **def-use** = def(定義)・use(使用) を追うプログラム解析。ここでは「そのライブラリが実際に
  使われている(import される)か」を判定する＝**imported**。
- 先行研究 Yu ら(DSN2024)は all 相当(pip install)の GT のみ作り、def-use(imported)は
  「実装すべき」と**提案だけ**した。Python 等は import が動的で難しいため。
- Go は import が静的＋`go list -deps` 内蔵なので imported が容易。
- **本研究の新規性**: `go list -deps` の発明ではなく、**all/imported/direct の3定義で SBOM ツール精度を
  系統的に比較し「最良ツールは正解定義で変わる」と Go で定量化した点**。（過大主張を避けた正確な表現。）
