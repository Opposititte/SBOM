# 分析計画（事前登録）— GT-imported が空である 123 件の層

**この文書は計測を実行する前に確定させたものである。** 出力を見てから分析規則を
決めることを避けるために、規則・対象・環境・失敗時の扱いをここで固定する。
確定の証跡は本文書を含むコミットのハッシュと日時とする。

---

## 1. 背景と目的

本研究の評価対象 1,528 件は「**GT-imported が空でない**」ことを条件に選別している
（`proc.sh:74` の `if [ ! -s gt_imported.txt ]`）。この条件により、
**`EMPTY_GT` として除外された 123 件**（go.mod には外部依存があるが、コードがどれも
import していないリポジトリ）が母集団から外れている。

これは方法論上の非対称である。GT-imported が空であれば、go.mod / go.sum を読む
Syft・Trivy が出力した依存は**すべて FP** となり precision は 0 になる。つまり
**Syft と Trivy にとって最も不利なケースが母集団から消えている**。
3つの GT 定義を比較する研究でありながら、そのうち1つ（GT-imported）が空でないことを
母集団の条件にしている、という構造になっている。

本計測の目的は、この 123 件を測定し、**主要結論（GT 定義によるツール順位の逆転）が
維持されるかを確認する感度分析**である。欠陥の修復ではなく、既存結論の頑健性の確認である。

## 2. 対象

`targets.csv` に凍結した 123 件。

| 層 | 件数 | 定義 |
|---|---:|---|
| `impT_nonempty` | 112 | GT-imported は空、GT-imported+test は非空 |
| `impT_empty` | 11 | GT-imported も GT-imported+test も空 |
| 合計 | 123 | いずれも GT-all は非空（`n_all > 1`） |

- 抽出条件: `manifest.csv` の `status == EMPTY_GT` かつ `n_all > 1`
- 全 123 件に 40 桁の commit SHA が記録されている（SHA 未記録は 0 件）
- `targets.csv` の SHA256:
  `d49264e2a5f4a9a03eaf75a1f23d15947ac3c391dcf5343c7b12c2e92b003e11`

## 3. 事前に固定する分析規則

### 3.1 GT-imported が空の層（123 件全件）

**precision / recall / F1 を主指標として平均しない。**

GT が空であれば定義上つねに `TP = 0`、`FN = 0` であり、非空の出力はすべて FP になる。
recall は `0/0` となって数学的に定義できない。これを無理に 0 や 1 に丸めると、
値そのものではなく丸め方が結論を決めてしまう。

代わりに次を報告する。

- ツール実行の成功件数 / NA（出力なし）件数
- 空の SBOM を出した件数
- 非空の SBOM を出した件数
- FP 数の中央値、四分位範囲（IQR）、合計
- 出力モジュール数の分布

### 3.2 GT-all（123 件全件）

123 件すべてで GT-all は非空であるため、**通常どおり precision / recall / F1 を計算する**。

### 3.3 GT-imported+test

- `impT_nonempty` の 112 件: **通常どおり precision / recall / F1 を計算する**
- `impT_empty` の 11 件: 3.1 と同じ空 GT 層として扱う

### 3.4 全体順位への影響を見る感度分析

123 件を既存 1,528 件に加えた場合に順位が変わるかを見るときに限り、Dice 形式を用いる。

$$F_1 = \frac{2\,TP}{2\,TP + FP + FN}$$

- 分母が正のときは通常どおり計算する
- `TP = FP = FN = 0`（GT も出力も空）のときは、**F1 = 0 とした場合と F1 = 1 とした場合の
  両方を報告する**。どちらか一方を正解として選ばない

これにより「空出力どうしを完全一致とみなして 1 にするか、情報なしとみなして 0 にするか」
という恣意性を、**上限と下限**として扱える。両方の場合で順位の逆転が維持されれば、
その結論は丸め方に依存しない。

### 3.5 主指標との関係

本感度分析は**副次的分析**であり、論文の主表（1,528 件）を置き換えない。
123 件は独立した層として報告し、既存の母集団へ黙って混ぜない。

## 4. 計測条件

`remeasurement-full` と同一とする。

| 項目 | 値 |
|---|---|
| Go | go1.26.5（`GOTOOLCHAIN=local`。新しい Go を要求する repo のみ `auto`） |
| `GOFLAGS` | `-mod=mod`（`go.work` がある repo では解除） |
| `GOOS` / `GOARCH` / `CGO_ENABLED` | `linux` / `amd64` / `1` |
| Syft | v1.46.0 |
| Trivy | v0.72.0（ビルドに `GOEXPERIMENT=jsonv2` が必要） |
| cdxgen | 12.7.1（Node.js v22.22.2） |
| cyclonedx-gomod | v1.10.0（mod モード） |
| module cache | **cold**（リポジトリごとに使い捨ての空 `GOMODCACHE`） |
| clone | `targets.csv` の commit SHA に固定 |
| timeout | 各コマンド 300 秒 |

module cache を cold とするのは `remeasurement-full` と条件を揃えるためである。
warm 条件では recall が上振れすることを対照実験で確認している
（`remeasurement-full/cache_effect/README.md`）。

## 5. 失敗時の扱い

`remeasurement-full` と同一の規則を用いる。

| 事象 | 扱い |
|---|---|
| clone / fetch の失敗 | retryable。3 回失敗したら permanent に降格し `skips.csv` に記録 |
| SHA が取得できない | permanent SKIP（対象 123 件には該当なし） |
| go.mod が無い | permanent SKIP |
| ツールが出力を出さない | NA として記録し、集計では 3.1 の「NA 件数」に数える |
| GT 生成の失敗 | `meta.json` の `exit_codes` と `stderr/` に記録し、集計から除外して件数を明示 |

SKIP が発生した場合は件数と理由を必ず報告し、母集団の欠落として明示する。

## 6. 保存するもの

`remeasurement-full` と同じ構造とする。

- リポジトリごとの GT 3 定義と 4 ツールの出力（TSV、2列: モジュールパス + バージョン）
- 生 SBOM（`raw/`、gzip）
- stderr（切り詰めなし）
- `meta.json`（SHA、実行時刻、各コマンドの終了コード、件数、環境）

## 7. この分析で主張しないこと

- 本分析は 123 件を主表に統合するためのものではない
- 空 GT に対する単一の F1 値を「正しい値」として提示しない
- FP 要因分類（`fp_test` / `fp_otherOS` 等）は行わない。
  `remeasurement-full` と同様に補助集合（`win.txt` / `mod_direct.txt` / `gosum.txt` 等）を
  保存しないため、これらの列は計算できない

## 8. 判定基準

次がすべて満たされれば、主要結論は 123 件の除外に対して頑健であると判断する。

1. GT-all において 123 件を加えても 4 ツールの順位が変わらない
2. GT-imported において、123 件を Dice 形式の下限（F1=0）で加えても上限（F1=1）で加えても、
   cdxgen / cyclonedx-gomod が Syft / Trivy を上回る関係が維持される

いずれかが満たされない場合は、その事実をそのまま報告する。

**FP の大小関係は合否基準に含めない**（理由は 9 節）。

## 9. 補助仮説 H3（合否基準ではない）

> **補助仮説 H3**: GT-imported が空の層では、Syft および Trivy の FP 数が
> cdxgen および cyclonedx-gomod より大きい傾向を示すと予想する。
> この仮説は RQ2 に対する補助的な整合性確認であり、**感度分析全体の合否基準とはしない**。
> 予想と異なる結果も変更せず報告する。

合否基準に入れない理由:

- 123 件は無作為な独立標本ではなく、「GT-imported が空」という条件で選ばれた層である
- FP 数はリポジトリの規模に影響される（大きい repo ほど FP が増えやすい）
- 同じツール・同じ GT 生成・同じ採点方法を用いるため、**独立した追試ではない**
- RQ2（情報源の違い）との整合は、GT-all における通常の P/R/F1 の方がより直接的に示す

### H3 の評価方法（絶対的なしきい値を用いない）

リポジトリ単位のペア比較として次を報告する。

- 勝ち / 同値 / 負けの件数
- FP 数の中央値と四分位範囲（IQR）
- ペア差の中央値
- GT-all に対する通常の P/R/F1

**記述統計のみとし、検定は行わない。** 検定を行う場合は、4 ツール間のどの比較を行うかを
事前に固定し、多重比較補正の方法も本計画に明記する必要があるが、補助分析にはそこまでの
厳密さを要さないと判断した。

## 10. 実装上の固定事項

分析規則とは別に、計測の実装条件も事前に固定する。

| 項目 | 固定値 |
|---|---|
| コマンド timeout | 各コマンド 300 秒（`remeasurement-full` と同一） |
| clone の再試行 | retryable な失敗は最大 3 回。超過したら permanent に降格 |
| main module の除外 | GT 側は生成時に `parseGt(out, gmain)` で除外。ツール側は採点時に `p === main` で除外（7月の `scorer.js` と同一） |
| 正規化 | `scorer.js` の `norm()` と同一（`decodeURIComponent` → `trim` → **小文字化**）。Trivy のみモジュールパスを小文字で出力するため、小文字化は必須 |
| module cache | リポジトリごとに使い捨ての空 `GOMODCACHE`（cold） |
| toolchain | `GOTOOLCHAIN=local`。`requires go >=` 系のエラーが出た repo のみ `auto` に切替え、`meta.json` に `toolchain_fallback` を記録 |
| 照合単位 | モジュールパス単位（name 一致）。バージョンは保存するが主指標には用いない |

### 件数報告の義務

次はいずれも**集計から黙って除外しない**。件数を必ず報告する。

- clone 失敗
- ツールの NA（プロセスが出力を残さなかった）
- SBOM の JSON 解析失敗
- GT 生成の失敗

とくに **「空の SBOM を出した」と「実行に失敗した」を区別する**。前者はツールが
「依存なし」と判断した結果であり、後者は測定できなかったことを意味する。
両者を混ぜると、空 GT 層では precision が定義できるかどうかが変わってしまう。

`meta.json` の `exit_codes` と `raw/` の有無で機械的に判別し、次の 3 状態で記録する。

| 状態 | 判定 |
|---|---|
| `ok_empty` | ツールは正常終了し、golang コンポーネントが 0 件 |
| `ok_nonempty` | ツールは正常終了し、golang コンポーネントが 1 件以上 |
| `na` | ツールが出力を残さなかった、または JSON 解析に失敗した |

### 集計の報告単位

**ツールごとの有効件数と、4 ツール共通集合の両方を報告する。** 母数の違いが順位に
影響していないことを確認するためであり、これは本編 1,528 件の分析（共通集合 n=1,467）と
同じ方針である。
