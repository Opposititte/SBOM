# 3層GT（all / imported / imported-test）× 4ツール — 全1489repo結果

awesome-go 評価対象 1489 repo を再クローンし、3つ目のGT `imported-test`（`go list -deps -test`）を生成。
ツール出力(syft/trivy/cdxgen/gomod)は resultsAll の既存結果を再利用（公表表を再現＋cdxgen23件クラッシュもそのまま）。
新ブランチ `claude/three-gt` ／ フォルダ `results3gt/`。生データ: `metrics3gt.csv`。

**方法の妥当性**: 再クローン版 imported と保存版 imported の drift は **93.5%の repoでゼロ**、平均0.37モジュール。再利用方式は妥当。
**注**: cdxgenの23クラッシュ・trivy6・gomod10 は出力ファイル無しのため本表の絶対値からは除外（公表値は0点算入で cdxgen 92.9、本表は除外で 94.3）。3GTの**差分**は同一repo集合で内部整合。

**読み方（芯Aの核心が3層で実証された）:**
- **GTにtestを足すと syft/trivy は F1が+9上がる**（test依存がFPでなくなる＝precisionが上がる）。
- **同じ操作で cdxgen/gomod は F1が約14下がる**（testを出さないので今度はFNになる＝recallが落ちる）。
- 2グループの差は **all で約20点(syft/trivy勝ち)→ imported で約26点(gomod/cdxgen勝ち)→ imported-test で約4点**まで圧縮。
- ⇒ **正解の定義(all / imported / imported-test)を変えるだけで、競争の構図が3通りに変わる**。「最も正確なツール」は正解定義なしに決まらない、を1本のスペクトラムで示せた。

- **gomod のFPは 間接-unused が77%で最大**、他OS(mousetrap型)は14%。

## ③ 芯B（失敗モード）の裏取り

- **cdxgen 23件0出力**: resultsAll の観測値（`go mod graph` 解析中の `Invalid purl` で全体破棄）。本3GT版でも同23件が出力ファイル無し(NA)として再現。
- **gomod「go mod why が GOOS無視で過剰報告」仮説**: 検証した。他OS-FP = **905モジュール = gomod FPの14%**。mousetrap型は**実在するが主因ではない**。gomod FPの主因は **間接-unused（4959モジュール=77%）**＝go.modに間接で書かれているが linux 非テストビルドで実際にはimportされない依存。
  → 芯Bは「観測ベース」に格上げ。ただし**主張は『OS盲目で過剰報告』ではなく『間接宣言-未importが主因（OS盲目は副次14%）』に修正**（量を見て初めて言える）。

## ④ 用途とGTの対応（フレームワークの骨子）

| 守りたいもの / 用途 | 適切なGT | その時の優位ツール |
|---|---|---|
| 本番バイナリの攻撃面（脆弱性スキャン） | imported | cdxgen / cyclonedx-gomod |
| CI・開発環境まで含む攻撃面 | imported-test | 差が縮小（全ツール接近、syft/trivyが追いつく） |
| ライセンス調査・全来歴 | all | syft / trivy |

→ どのツールが「正確」かは技術では決まらず、**何を守りたいか（=どのGTを正解とするか）で決まる**。
