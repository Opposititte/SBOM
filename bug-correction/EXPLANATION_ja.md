# 自モジュール除外漏れ — 何が起きたかの説明

対象: 7月計測（`census2`, 1,528 repo）／該当 **7 repo**
この文書は「論文をどう直すか」ではなく、**なぜ値が動くのかを一つの具体例で理解する**ためのもの。
読んで納得できなければ、値は変更しない（末尾「判断」を参照）。

## 1. 何が間違っていたか

評価では「対象プロジェクト自身のモジュール（= main module）」を依存ライブラリから除外する必要がある。
`github.com/Lifailon/lazyjournal` を評価するとき、`github.com/Lifailon/lazyjournal` 自身は依存ではない。

7月のパイプラインでは、この除外が **2つの独立した場所** で行われていた。

| 場所 | 対象 | 実装 |
|---|---|---|
| 収集時 | GT-imported / GT-imported+test | `proc.sh:66-67` の `grep -v "^${gmain} \?$"` |
| 採点時 | GT-all・**4ツールの出力すべて** | `scorer.js:14,17,24` の `if (p === main) continue` |

`scorer.js` は main module 名を `main.txt` という1つのファイルから読む（`scorer.js:9`）。
7 repo では、採点時にこの `main.txt` が空だった。

その結果:

- **GT-imported / impT** は無事だった。収集時の `grep` が既に自分自身を落としていたため（2重防御の1枚目が生きていた）。
- **GT-all** は壊れた。`proc.sh:65` の `go list -m -e all` は生出力のままで `grep` を通していない。除外は `scorer.js` 頼み1枚だけ。→ GT-all に自分自身が1件混入。
- **ツール出力側** も壊れた。こちらも除外は `scorer.js` 頼み1枚だけ。→ ツールが自分自身を出力していた場合、それが依存として数えられた。

つまり「除外が二重になっていた側は助かり、一重だった側だけが壊れた」。
損傷のパターンが実測とぴったり一致する（後述3節）。

### 具体例: `Lifailon__lazyjournal`

- 正しい依存（GT-imported）は 10 件。
- 7月の GT-all は 21 件（`manifest.csv` の `n_all` も 21）。再計測で自分自身を正しく除いた GT-all は **20 件**。差の1件が `github.com/Lifailon/lazyjournal` 自身。
- Syft の生 SBOM（`remeasurement-full/out/Lifailon__lazyjournal/raw/syft.json.gz`）には golang コンポーネントが 12 件あり、**その1件目が `github.com/Lifailon/lazyjournal`** — プロジェクト自身。7月はこれを依存として採点していた。

### 「main.txt はなぜ空だったのか」

ここは正直に書く。**根本原因は復元できない。**
`proc.sh:80` が作業ディレクトリを毎回削除しているため、7月の `main.txt` は現存しない。
`manifest.csv` の `main_module` 列にはこの7 repo でも正しいモジュール名が入っている（`proc.sh:35` の `$gmain` は取れていた）。
したがって「`go list -m` が失敗した」のではなく、**`proc.sh:36` で書いた `main.txt` が、`proc.sh:79` で `scorer.js` が読むまでの間に失われた**ことになる。
このスクリプトはディスク空き 1.5GB を切ると中断するほどの逼迫下で動いており（`proc.sh:53-58`）、書き込み失敗を検査していない。ディスク逼迫による書き込み失敗が最有力だが、**これは仮説であり証拠はない**。

原因が不明でも、**影響の検出は網羅的にできる**（次節）。

## 2. なぜ 7 件だけなのか

「7件を選んだ」のではなく、**1,528 repo 全件に機械的な判定式を当てて、該当したのが 7 件**だった。

判定式:

```
manifest.csv の n_all （= gt_all.txt の行数。自分自身を含む生の数）
  − scorer が実際に採点した GT-all の件数（= tp + fn）
    == 0  →  自分自身が除外されていない
    == 1  →  正しく除外されている（正常）
```

- 正常な repo はすべて差が 1 になる。
- 差が 0 の repo が 7 件。`Lifailon__lazyjournal` / `antonmedv__fx` / `box-cli-maker__box-cli-maker` / `dghubble__sling` / `dtgorski__typex` / `homedepot__flop` / `naughtygopher__errors`。

この判定は**結果を見る前に**決めて全件に当てた（`remeasurement-full/verify_lib.js` の `emptyMainRepos()`）。
その後 1,528 repo を再計測して 7月の値と3値分類（一致／既知の main 不具合／不一致）で突き合わせた結果、
**一致 6,033 行（98.9%）、この不具合 24 行、説明のつかない不一致 4 行**。
つまり「他にも同種の誤りが隠れている」可能性は、この観点では潰してある。

**唯一の盲点**: 判定式は `n_all > 0` を要求するので、`n_all = 0` の repo（`kubernetes` 1件）は判定できない。
逆に言えば、この1件を除き全件検査済み。

## 3. 各ツールで TP・FP・FN のどれが変わるのか

自分自身の1件がどこに現れるかは、**そのツールが自分自身を SBOM に出力するかどうか**で決まる。

| ツール | 自分自身を出力するか | GT-all | GT-imported | GT-imported+test |
|---|---|---|---|---|
| **syft** | する | GT にも出力にも有る → **TP** だった。両方から消える → `all TP −1` | GT に無く出力に有る → **FP** だった → `imp FP −1` | 同左 → `impT FP −1` |
| **trivy** | する | 同上 `all TP −1` | 同上 `imp FP −1` | 同上 `impT FP −1` |
| **cdxgen** | しない | GT にだけ有る → **FN** だった → `all FN −1` | 変化なし | 変化なし |
| **cyclonedx-gomod** | しない | 同上 `all FN −1` | 変化なし | 変化なし |

**重要**: 補正はすべて **減算のみ**。新しい TP も新しい FP も生まれない。
「余計な1件を両側から取り除く」以上のことは何もしていない。

実測（`Lifailon__lazyjournal`, name一致）:

| ツール | 列 | 7月 | 補正後 |
|---|---|---:|---:|
| syft | `n_all_tp` | 12 | 11 |
| syft | `n_imp_fp` | 2 | 1 |
| syft | `n_impT_fp` | 2 | 1 |
| trivy | `n_all_tp` | 11 | 10 |
| trivy | `n_imp_fp` | 1 | 0 |
| trivy | `n_impT_fp` | 1 | 0 |
| cdxgen | `n_all_fn` | 11 | 10 |
| cyclonedx-gomod | `n_all_fn` | 11 | 10 |

version一致（`v_*`）も同じ動き。全 6 repo 分で **103 セル**（`evidence_cell_changes.csv`）。

### 補正値を「7月の生 SBOM 無し」で出せる理由

7月の生 SBOM は削除済み。そこで再計測（同一コミット SHA を固定して取得）の生 SBOM を使い、

1. **main を空にして** `scorer.js` で採点 → 7月の記録 18 列と一致するか照合
2. 一致した行だけ、**main を正しく与えて**採点した値に差し替える

6 repo × 4ツール × 18列 = 432 値がすべて一致した（`evidence_decisions.csv`）。

**この一致が意味すること／意味しないこと**（前に言い過ぎたので訂正済み）:
- 意味する: 採点に効く範囲でツール出力は7月と同等。補正値は信頼できる。
- 意味しない: 生 SBOM がバイト単位で同一である証明ではない。あくまで**採点等価**。

### 7件目 `homedepot__flop` だけ扱いが違う

このrepoは7月に commit SHA を記録し損ねており（`manifest.csv` の `commit_sha` が空）、
同じコードを取り直せないため再計測を SKIP した。よって上の照合ができない。
ただし方向は**算術的に一意に決まる**:

- syft / trivy: 7月の `all FN = 0` → `FN−1` は不可能 → 「自分自身を出力していた」側で確定
- cdxgen / cyclonedx-gomod: 7月の `imp FP = 0` → `FP−1` は不可能 → 「出力していなかった」側で確定

（`evidence_forced_scenario.csv`）。念のため両シナリオの上下限も計算してあり、
小数第1位の掲載精度ではほぼ一意（唯一 cyclonedx-gomod の GT-imported が 94.4/94.5 で割れるが、
上の確定により 94.5 = 7月と同じ）。`unresolved_bounds.csv` 参照。

## 4. なぜ 35 個の掲載値へ波及するのか

**35 個の別々の誤りではない。7 repo の「余分な1モジュール」1種類が、集計を経て 35 箇所に顔を出しているだけ。**

| 掲載物 | 何を出しているか | なぜ動くか | 変化した数 |
|---|---|---|---:|
| 表A.3 | TP/FP/FN の**素の合計** | 103セルの減算がそのまま合計に効く。**必ず動く** | 11 |
| 表6・表A.1・表A.2 | 1,528 repo の**平均**（macro/micro） | 1 repo の寄与は約 1/1500。平均は 0.0x pt しか動かないが、**小数第1位の丸め境界をまたいだ組合せだけ**表示が 0.1 変わる | 11 |
| 表7 | 共通集合での平均 | 同上 | 4 |
| 表A.4 | FP要因分類 | FP合計（分母）が動く。内訳%は7月の分子のまま → **混合値になる** | 5 |
| 6.4節 | Wilcoxon | F1 が動いた repo が勝敗の境界をまたぐと、勝敗数・中央値差・効果量が最小単位だけ動く | 4 |

だから表A.3（生の数）は 11 箇所全部動くのに、表6（平均）は 4 箇所しか動かない。
**「たまたま丸め境界に乗っていたセルだけが動く」**というのが 35 という数の正体。

## 5. 論文の主張が変わらない理由

1. **順位が一切変わらない。** 全表・全 GT 定義で 4ツールの並び順は補正前後で同一。
2. **変化幅が最大 0.1 ポイント。** 割合の値で 0.1 を超えて動いたものは1つも無い。
   素の合計も最大 7 件の減少（例: syft `all TP` 76,929 → 76,922 ＝ 0.009%）。
3. **統計的結論が変わらない。** p 値・z 値はすべて不変（すべて `p < 1e-15` ないし `6.2e-5`）。
   効果量は 1 箇所が 0.97 → 0.98 に動いただけ。
4. **論文の中心主張は数十ポイント差の上に立っている。**
   「GT 定義を GT-imported から GT-all に変えると cdxgen と syft の優劣が逆転する」という主張の差は
   中央値差 23.1pt と 18.7pt。0.1pt の補正で揺らぐ距離ではない。
5. **補正は減算のみ**なので、どのツールにも系統的に有利／不利には働かない。
   syft・trivy は FP が減る（有利）と同時に TP も減る（不利）。

要するに、**この不具合は「精度の推定値が第1位の丸めで最大1目盛りずれていた」という水準**であり、
どのツールが優れているか・GT 定義が結論を左右するか、という論文の問いには影響しない。

## 判断: 値は変更せず、限界として明記する

**結論（確定）: 7月の掲載値はそのままとし、限界に1文を加える。**

> 1,528件中7件で自モジュールの除外が不完全であった。補正して再集計した結果、
> macro P/R/F1の変化は最大0.1ポイントであり、ツール順位および主要結論は変わらなかった。

この文の各主張の裏付け:

| 主張 | 裏付け |
|---|---|
| 「1,528件中7件」 | 全件に判定式を適用（2節）。`n_all=0` の kubernetes 1件のみ適用外だが集計上NA |
| 「補正して再集計した」 | 6件は再計測の生SBOMで照合してから差し替え、1件は算術で方向確定（3節） |
| 「macro P/R/F1 最大0.1pt」 | 表6・表A.1・表A.2・表7 で動いた値はすべて0.1。0.1超は皆無（6節） |
| 「順位および主要結論は不変」 | 全表・全GT定義で順位同一、p値・z値すべて不変（5節） |

**この文が主張していない範囲**: 表A.3（TP/FP/FNの素の合計）は最大7件減る（syft `all TP` 76,929→76,922、0.009%）。
表A.3 も他の値と同じ手順で補正済みであり（`paper_values_diff.csv` の11行）、
自モジュール1件分の増減は7月の記録から確定するので、検証できないわけではない。
上の限界文が割合指標だけを述べているため、表A.3に言及する必要がないというだけである。

**発表で「どうやって7件と特定したのか」と聞かれたら**:
「`manifest.csv` の `n_all`（自分自身を含む生の件数）と、採点された GT-all の件数の差を全件で取った。
正しく除外されていれば差は1、除外漏れなら0。差が0だったのが7件」と答え、
必要なら `bug-correction/` の CSV を示す。

### なぜ35箇所を書き換えないのか

1. **0節の訂正が示したとおり、私の集計スクリプト自体に2回の取りこぼしがあった。**
   「全掲載値を比較した」と称したものに漏れがあった以上、
   「これで全部です」と保証できる段階に達していない。
2. **表A.4 は補正が混合値になる**（分子は7月・分母は補正後）。整合的に直せない。
3. 書き換えれば本文・表・付録の整合を人手で取り直すことになり、
   そこで新たな不整合を作り込む risk の方が、0.1pt の精度向上より大きい。
