# cyclonedx-gomod app vs mod — awesome-go 全件（2225 repos）結果

awesome-go の gomod=ok 全 **2225 repos** で計測（40件パイロットの全件版）。
各 repo を新規クローンし、同一クローンから GT-imported(linux)・GT-all・`app`・`mod` を生成。
再開可能バッチ（25件ごと増分push）。途中コンテナリセットが1回発生したが、push済みデータから復元し完走。
生データ: `results_appmod_full/appmod_full.csv`。

## 1. カバレッジ（app はそもそも動くか）

| 種別 | 件数 | app 出力 |
|---|---:|---|
| ライブラリ（本物のmain無し） | **1165** | 不可 |
| app 実行失敗（mainありエラー） | 161 | 不可 |
| アプリ root（モジュール直下がmain） | 308 | 可 |
| アプリ cmd/*（cmd配下にmain） | 404 | 可 |
| アプリ その他 | 187 | 可 |
| **合計** | **2225** | |

- **app が出力できたのは 899 / 2225（40%）だけ**。`mod` は **2225 / 2225（100%）**。
- ライブラリが **1165件（52%）** ＝ awesome-go の過半数。app は main 必須なので構造的に動かない。

## 2. 精度（vs GT-imported(linux), マクロ平均）

| 対象集合 | ツール | Precision | Recall | F1 |
|---|---|---:|---:|---:|
| **全評価対象（依存あり, n=1490）** | **mod** | 0.914 | 0.983 | **0.935** |
| **単一バイナリ的アプリ (n=562)** | **app** | **0.999** | **0.988** | **0.993** |
| 〃 | mod | 0.921 | 0.994 | 0.948 |
| app出力ありの全 (n≈789) | app | 0.925 | 0.807 | 0.833 |
| 〃 | mod | 0.904 | 0.985 | 0.932 |

- **単一バイナリのアプリでは app がほぼ満点（F1=0.993）** ＝ ビルド制約を評価し linux で実際にリンクする依存だけを出すため imported(linux) とほぼ完全一致。mod(0.948) を上回る。
- **複数バイナリ repo（222件）では app の recall が落ちる（0.807）**。app＝1バイナリの依存閉包、GT-imported＝`go list ./...`＝**リポジトリ全体**の import → **スコープの違い**であり app の欠陥ではない。
- そのため app出力ありの全体では mod(0.932) > app(0.833)。

## 3. vs GT-all（参考, app出力あり集合 n=815）

|---|---:|---:|---:|
| app | 0.859 | 0.301 | 0.413 |

all は「全部入り」のため両者とも recall が低い。mod の方がやや多く拾う。

## 4. 確定した結論（使い分け）

1. **リポジトリ単位・GT=モジュール全体・ライブラリ主体の本研究 → `mod` が正しい。**
   - app はライブラリ（52%）で動かず**カバレッジ40%**。mod は**100%**。
   - GT がモジュール全体スコープなので全パッケージ集約の mod が構造的に一致（**F1=0.935 vs imported**）。
   - → 本番 1489件で `mod` を採用したのは妥当。**全2225件で確認済み。**
2. **「1つの出荷バイナリの SBOM」が単位なら → `app`。**
   - ビルド制約評価で imported(linux) とほぼ完全一致（**F1=0.993**）。mod の他OS過剰報告を解消。
3. **スコープ（1バイナリ vs モジュール全体）を GT に合わせるのが大前提。**
