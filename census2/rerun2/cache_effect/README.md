# module cache 状態が SBOM ツールの出力に与える影響（対照実験）

`cache_effect.js` の結果。同一 commit SHA・同一マシン・同一ツールバイナリで、
**Go module cache の状態だけ**を変えて4ツールを実行した対照実験。

## 条件

| | 内容 |
|---|---|
| cold | 使い捨ての空 `GOMODCACHE` でツールを実行（rerun2 本計測の条件） |
| warm | 同じ repo で `go mod download all` を済ませてから同じコマンドを実行 |

標本は rerun2 のシード固定シャッフル順の先頭連続区間（＝無作為標本）から等間隔抽出した
**114 リポジトリ × 4 ツール = 456 行**。

> warm は7月の共有キャッシュと**等価ではない**。7月の `proc.sh` は
> `GOMODCACHE=/tmp/rm_modcache` を全 1,528 件で共有していたので、ある repo を処理する時点で
> キャッシュにあるのは「**それまでに処理した他の repo の依存**」であり、その repo 固有の依存は
> 入っていない。ここでの warm は「その repo の依存が全部ある」上限側の条件。
> この実験で測っているのは7月の再現ではなく、**キャッシュ状態に対する感度**である。

## 結果

冷/温で出力が変わった repo の割合（95% CI は Wilson score interval）:

| ツール | 変化した repo | 割合 | 95% CI |
|---|---|---|---|
| syft | 1 / 114 | 0.9% | [0.2, 4.8] |
| trivy | 3 / 112 | 2.7% | [0.9, 7.6] |
| cdxgen | 0 / 113 | 0.0% | [0.0, 3.3] |
| cyclonedx-gomod | 0 / 113 | 0.0% | [0.0, 3.3] |
| **全体（repo×tool 行）** | **5 / 452** | **1.11%** | **[0.5, 2.6]** |

健全性チェック: cold の結果は本計測（`out/`）の保存値と **159/160 で完全一致**
（残り1件は元から NA）。ハーネスは決定論的に動いている。

### 効果の向き（ここが本質）

- 温めて**増えた**モジュールは **11 件すべてが GT-all に含まれる真の依存**。
  温めて**減った**モジュールは **0 件**。
  → ランダムな揺らぎではなく、**recall を上げる方向にのみ働く系統的バイアス**。
- 当たったときの振れ幅は大きい。trivy の GT-all に対する recall:
  - `awnumar__memguard` 57% → 100%
  - `peterstace__simplefeatures` 67% → 100%
  - `g4s8__envdoc` 79% → 100%
- モジュール検出だけでなく**ツールの成否**も変わる:
  `fern4lvarez__piladb` の cyclonedx-gomod は cold で NA（失敗）、warm で成功（2件検出）。

## 数字の書き方（重要）

- ❌ 「効果は5%未満」「しきい値5%を明確に下回る」
  → **書いてはいけない。** trivy の CI 上限は 7.6% で 5% を超えており、
    n=114 では「5%未満」と断定する精度がない。
- ✅ 「点推定 1.1%（95% CI [0.5, 2.6]）、ツール別でも点推定は 3% 以下。
    ただし trivy は上限 7.6% で、稀だが無視できない可能性を排除できない」

「5%」という線引きは **383 件を再計測するコストに見合うかという運用判断の閾値**であって、
統計的有意性の基準ではない。**続行判断の根拠としては妥当だが、論文の主張には流用しないこと。**

## cold を採用した理由（原稿での書き方）

コスト判断（「効果が小さいから cold のまま」）を理由として書くと査読で刺さる。
実際、**現実の利用場面ではキャッシュは温まっている**（開発者は自分がビルドした repo に
ツールを掛ける）ので、cold は clean-room 条件であって標準ではない。

原稿ではこう位置づける:

> 本研究ではキャッシュ未取得の状態を**統制条件**として採用した。実利用に近い warm 条件では
> recall が上振れすることを対照実験で確認しており（増えた依存はすべて真の依存、減ったものは
> 0 件）、したがって本研究が報告する値は**保守側（過小評価側）に寄る**。

こう書けば cold であることは弱点ではなく設計になる。

## 7月の計測への含意

7月の `proc.sh` は全 1,528 件で `GOMODCACHE` を共有していたため、キャッシュは処理が進むほど
温まる。つまり**7月の値は処理順に依存**しており、後半に処理された repo ほど recall が
上振れしていた可能性がある。7月の条件は原理的に再現不能（順序依存）であり、
「7月と一致すること」を合格条件に据えられないと判断した根拠でもある。

## 未確認の派生仮説

7月に「一部ツールのみ NA」だった 53 件（cdxgen 27 / cyclonedx-gomod 19 / trivy 11 / syft 1）
のうち、いくらかは**キャッシュ由来の失敗**である可能性がある
（`fern4lvarez__piladb` で cold=NA → warm=成功 を観測済み）。
ツールの失敗率という別指標にも効くため、数件で確かめる価値がある。→ `na_probe.js`


## キャッシュでは説明できない trivy の -1 パターン（別現象）

本計測中に、**キャッシュ状態と無関係な** trivy 固有の差分が見つかっている。署名は一定:

- trivy だけが GT-all の TP を **ちょうど1件** 7月より少なく報告する
- GT 3定義の件数は7月と完全一致（GT 側の差ではない）
- 他の3ツールは7月と完全一致
- 欠けている側は必ず go.mod 直記載ではなく **go.sum 由来の推移的依存**
- cold / warm で同結果。`shenwei356__taxonkit` では go.sum の全74モジュールを
  module cache に入れても変化せず、キャッシュ起因を明確に否定できる
- trivy を5回実行しても出力集合は完全に同一（md5一致）＝非決定性でもない

該当: `abice__go-enum`, `shenwei356__taxonkit`（774件中2件 ≈ 0.3%）

**どのモジュールが欠けたかは特定できない。** 7月は生SBOMを保存しておらず tp/fp/fn の
件数しか残っていないため。rerun2 は `raw/` に生SBOMを gzip 保存しているので、
今後の比較では特定可能になる。7月の記録粒度の不足が、そのまま診断能力の限界になっている例。

原稿では「再現できなかった差分」として件数と署名を正直に報告するのが妥当。
原因不明であること自体は、SBOM ツールの評価が再現困難であるという本研究の論点を補強する。
